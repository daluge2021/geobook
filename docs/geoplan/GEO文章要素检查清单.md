# GEO 文章要素检查清单

> 本文档基于 GEO Encyclopedia（geo010.com）的实战规范整理，适用于面向 AI 引擎（ChatGPT、Google AI Overviews、Perplexity、Grok 等）检索、引用、推荐的英文 GEO 静态页面。

## 1. 核心原则（GEO 技术原理）

GEO 的核心目标是：**让一篇页面成为「可被 AI 单独引用的答案资产（Answer Asset）」**。

AI 在 RAG/检索时，往往不会整页抓取，而是：

- **按区块检索**：优先抓取页面中的小标题（H2/H3）及其邻近段落。
- **答案前置**：AI 倾向直接摘录「开门见山」的结论，而不是长篇背景铺垫。
- **结构化易解析**：列表、表格、定义块、FAQ 等结构更容易被解析成引用片段。
- **可验证性优先**：带有明确来源、数据、案例的内容更容易被优先引用。

因此，GEO 写作要遵循：**「一页一主题（Single Intent）」「每个 H2 一个独立答案」「答案前置，结构清晰」**。

## 2. 标题与整体结构

| 检查项 | 要求 | 检查（是/否） |
|---|---|---|
| **H1 唯一且聚焦** | `H1` 简短、有力，直指页面核心查询意图（≤110 字符）。避免「概述」「简介」这类泛化用语。 | □ 是  □ 否 |
| **一页一主题** | 整页只围绕**单一用户查询**展开。不要把多个不相关主题堆在同一页面。 | □ 是  □ 否 |
| **H2 问题式** | `H2` 尽量用疑问形式（What/How/Why/Which/When/Do/Can/Should）。优先用**自然语言提问**而不是纯名词。 | □ 是  □ 否 |
| **H2 覆盖全貌** | `H2` 顺序能清晰勾勒读者（或 AI）想了解的要点，且每个 `H2` 都能独立成「一个可引用的答案」。 | □ 是  □ 否 |
| **H3 精准细分** | 仅在需要进一步拆解时用 `H3`。若 `H3` 内容也很短且能成独立答案，也可考虑升格为 `H2`。 | □ 是  □ 否 |

> **反例**：H2 为 `Citation Share Metrics`（纯名词）→ 建议改为 `What is Citation Share in GEO?` 或 `How is Citation Share Measured?`

## 3. 开场、答案前置与场景化

| 检查项 | 要求 | 检查（是/否） |
|---|---|---|
| **场景化开场（首选）** | 文章首段用**虚拟场景、真实困惑或用户提问**自然带入，而不是「This article introduces...」。 | □ 是  □ 否 |
| **答案前置（强制）** | 每个 `H2` 下的**首 1～2 句**必须直接给出答案（结论），再展开解释、论据、例子。 | □ 是  □ 否 |
| **定义前置** | 若涉及核心概念（如 GEO、AIO、Citations），首个定义应**尽早出现**，且用简短、精确的表述。 | □ 是  □ 否 |
| **关键定义突出** | 用 `<blockquote><strong>...</strong></blockquote>` 标注**核心定义、判定标准、简短结论**。这类极短句最常被 AI 直接引用。 | □ 是  □ 否 |

> **原理**：AI 在截取片段时，若首句已是答案，即使只返回前 2～4 行也能保留核心观点。

## 4. 内容要素（论证、数据、来源）

| 检查项 | 要求 | 检查（是/否） |
|---|---|---|
| **段落精短** | 每段 ≤ **6 行**（约 ≤ 440 字符）。长句要拆成短句，避免大段纯散文。 | □ 是  □ 否 |
| **术语全称** | 首次出现英文专业术语时，附上全称：`Generative Engine Optimization (GEO)`、`Artificial Intelligence Overviews (AIOs)`。后续可直接用缩写。 | □ 是  □ 否 |
| **可验证来源** | 凡是「研究表明」「数据显示」「行业报告指出」等表述，**必须标注来源**（机构名、报告名、年份，或可直接点击的外部链接）。 | □ 是  □ 否 |
| **案例支撑** | 涉及实操建议时，优先用**具体场景/案例**说明，而不是空泛「建议做...」。 | □ 是  □ 否 |
| **对比清晰** | 若对比 GEO vs SEO、AIO vs Featured Snippets 等，**用表格呈现**差异（维度、触发方式、计量方式、影响等）。 | □ 是  □ 否 |
| **数据结构化** | 数值、占比、排名、漏斗类信息优先用 `<table>` 而不是纯文本段落。表格更利于 AI 抽取要点。 | □ 是  □ 否 |
| **列表增强可读性** | 操作步骤、清单、要点用 `<ul>/<ol>`。每条尽量简短（1～2 行）。 | □ 是  □ 否 |
| **结尾总结** | 页面末尾加**1～2 句话的总结**（如「In short: ...」「Key takeaway: ...」），概括核心结论，便于 AI 作「最终简答」时引用。 | □ 是  □ 否 |

## 5. FAQ、问答与结构化标记

| 检查项 | 要求 | 检查（是/否） |
|---|---|---|
| **问答式段落** | 对高频疑问（用户常搜的「what/how/why」）直接用**问题+简答**形式组织，符合自然提问习惯。 | □ 是  □ 否 |
| **FAQ 区块** | 若页面涵盖 2 个以上常见问题，建议显式新增 `## FAQ` 或 `<section>`，每个子项用简洁问答。 | □ 是  □ 否 |
| **FAQPage JSON-LD（推荐）** | 问答类页面**强烈建议**在 `<head>` 增加 `FAQPage` JSON-LD。问题文本需与页面上实际展示的 H2/FAQ 标题**保持一致**。 | □ 是  □ 否 |
| **Article JSON-LD** | 文章页应包含 `Article`（或 `TechArticle`）JSON-LD，字段至少涵盖 `headline`、`author`、`publisher`、`datePublished`、`dateModified`、`mainEntityOfPage`、`inLanguage: "en"`。 | □ 是  □ 否 |
| **BreadcrumbList JSON-LD** | 有面包屑时同步 `BreadcrumbList` JSON-LD，`itemListElement` 路径与实际导航一致。 | □ 是  □ 否 |
| **代码块最小化** | 仅在真正需要展示可复用代码（如 JSON、HTML 片段）时才用 `<pre><code>`。日常说明不应堆砌大段代码。 | □ 是  □ 否 |

## 6. 元数据、时间戳与索引同步

| 检查项 | 要求 | 检查（是/否） |
|---|---|---|
| **canonical** | `<head>` 必须有 `<link rel="canonical" href="https://your-domain.com/path/page.html">`，指向**最终落地 URL**。 | □ 是  □ 否 |
| **RSS alternate** | `<head>` 须包含 `<link rel="alternate" type="application/rss+xml" title="..." href="https://your-domain.com/feed.xml">`（保持站点统一标题）。 | □ 是  □ 否 |
| **datePublished/dateModified 正确** | `datePublished` 保持**首次创建日**不变。`dateModified` 更新为**本次实际修改日**（YYYY-MM-DD）。 | □ 是  □ 否 |
| **sitemap.xml 同步** | 修改页面后，检查 `sitemap.xml` 中对应条目的 `<lastmod>` 是否已更新为本次修改日。 | □ 是  □ 否 |
| **站内索引同步** | 根据实际改动同步以下文件：`index.html`（侧边栏/章节列表）、`llms.txt`、`feed.xml`、`summary.json`。如新增页面，需一并更新。 | □ 是  □ 否 |
| **.well-known 一致性（如适用）** | 若站点提供 AI 相关发现文件（`ai.txt`、`ai.json`、`llms.txt`、`ai-plugin.json`、`openapi.json`），需按站点实际情况核对是否需要更新。 | □ 是  □ 否 |

## 7. 页面交互、导航与站点规范

| 检查项 | 要求 | 检查（是/否） |
|---|---|---|
| **面包屑** | 文章页通常应有简短面包屑（`Home > Chapter > Article`），便于用户与爬虫理解路径。术语页等极简页可酌情保留，但**新生成的文章页应保留**。 | □ 是  □ 否 |
| **上下篇导航（.nav-links）** | 章节内文章建议保留 `.nav-links`（Previous/Next），增强页面间语义关联。 | □ 是  □ 否 |
| **当前页高亮** | 若页面出现在侧边栏，需正确标注 `class="active"`，保持导航一致。 | □ 是  □ 否 |
| **内联 CSS** | 静态站点优先沿用「全内联 `<style>`」的极简方案（本项目规范）。引入外部 CSS/JS 前需评估是否真有必要。 | □ 是  □ 否 |
| **图片规范** | `<img>` 必须加 `alt`（描述性英文），且 `max-width: 100%`。避免无关装饰图、避免外链大图。 | □ 是  □ 否 |
| **统计脚本保留** | 若站点已有访问统计（如 51.la），**绝对不要删除或修改**统计脚本。仅按原位置保留。 | □ 是  □ 否 |
| **隐私页例外** | `monitor.html`、`stats.html` 等纯统计/隐私页可刻意精简（如不加部分 JSON-LD），这是**故意设计的例外**，不适用于普通文章页。 | □ 知悉（例外） |

## 8. GEO 反模式（命中即需修复）

| 反模式 | 原因 | 是否命中 |
|---|---|---|
| **纯散文，无小标题** | AI 无法精准定位「哪个段落回答哪个问题」。极易被整页丢弃或只截取模糊片段。 | □ 是  □ 否 |
| **答案埋在中间** | 要等读完整段落才知结论。RAG 常只取 H2 下前几行，导致核心观点被切掉。 | □ 是  □ 否 |
| **「本文将介绍...」式开场** | 太自我、太模板化。用户（和 AI）更关心「答案是什么」而不是「文章目的」。 | □ 是  □ 否 |
| **观点无来源** | 「研究表明」「业内普遍认为」却无出处。AI 更倾向引用**可验证**的内容。 | □ 是  □ 否 |
| **一页多主题** | 查询意图不聚焦。难以匹配特定用户提问，也降低单个页面成为「权威答案」的概率。 | □ 是  □ 否 |
| **长段落（>6 行）** | 降低可读性，也不利于 AI 按语义切分成可引用片段。 | □ 是  □ 否 |
| **堆砌缩写未解释** | 假定读者已知缩写。首次出现必须给全称。 | □ 是  □ 否 |
| **数据纯文本堆砌** | 对比、清单类信息用表格/列表远比大段文字更利于抽取。 | □ 是  □ 否 |
| **标题纯名词无疑问** | 问题式 H2 更贴近真实搜索提问（长尾、自然语言），也更符合「直接回答问题」的预期。 | □ 是  □ 否 |

## 9. 校验流程（实操建议）

推荐按以下顺序逐项检查：

1. **定大纲**：先列出 `H1 + 全部 H2`（全部用问题式思考），确认**一页一主题**。
2. **逐节写作**：每个 H2 → **首句直接给答案** → 短段落展开 → 必要时用列表/表格/blockquote。
3. **要素补足**：补充术语全称、来源链接、定义块、结尾总结。
4. **结构化校验**：检查 JSON-LD、canonical、RSS、日期（`datePublished` 不变，`dateModified` 更新）。
5. **索引同步**：同步 `sitemap.xml`（`<lastmod>`）、`index.html`、`llms.txt`、`feed.xml`、`summary.json`（必要时 `.well-known/`）。
6. **自动+人工**：跑项目自带校验脚本（如 `.opencode/skills/geo-content-format/references/check_content_format.mjs`）＋本清单全量复核。
7. **回归检查**：发布前再走 `geo-review` 相关回归清单（统计脚本保留、品牌一致、无中文等）。

## 附录：最小可用「通过标准」

一篇**新生成**的 GEO 文章，建议至少满足以下硬门槛再发布：

- [ ] **H1 聚焦 + 全部 H2 问题式**（且一页一主题）
- [ ] **每个 H2 首句答案前置**
- [ ] **段落 ≤ 6 行**（全页大部分段落达标）
- [ ] **关键定义用 `<blockquote><strong>` 标注**
- [ ] **数据/对比用表格**（如有对比场景）
- [ ] **术语首次出现附全称**
- [ ] **来源标注齐全**（有数据/论断时）
- [ ] **结尾总结 1～2 句**
- [ ] **JSON-LD（Article + 必要时 FAQPage/BreadcrumbList）齐全且字段正确**
- [ ] **canonical + RSS alternate + datePublished/dateModified 正确**
- [ ] **sitemap.xml `<lastmod>` 与 `dateModified` 一致**
- [ ] **`.nav-links`（章节内）齐全**
- [ ] **统计脚本未改动（如存在）**

> **提示**：脚本能查「有无」但查不出「是否答案前置」「是否场景化」「来源是否充分」。**自动校验≠人工把关**，两者都要做。
