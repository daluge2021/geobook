How I Built a RAG Knowledge Base That Passed 100% of Its Own Eval — 6 Debugging Lessons

A RAG knowledge base is only as good as its evaluation — without a measurable eval, every tuning change is a coin flip.
This merged field report (Reddit + LinkedIn) covers a Retrieval-Augmented Generation (RAG) system built from scratch on SQLite + numpy that scored 100% on a self-written 12-question eval.
The score is not the point. The six debugging lessons — alias normalization, ordering bias, vector blind spots, table blindness, query expansion, and post-check false positives — are the transferable part.
Demo data only: the build ran on a fictional REDMI K90 series dataset as an engineering exercise, not a real product review. All figures are illustrative.

What Did This RAG Build Actually Do?

It built a question-answering knowledge base over a small product dataset that passed every check in its own evaluation — 12 questions, 6 checks each, iterating 94.4% → 98.6% → 100%. No vector database was involved; the whole engine is about 600 lines of Python over SQLite and numpy.

The reason this matters beyond a toy: grounding LLMs in your own data is becoming everyone's default problem, and most "hallucination" complaints are really data and retrieval problems wearing the model's face.

Why Should the Relational DB Be the Source of Truth?

Because business facts are deterministic, and vectors should only handle fuzzy semantics. Entities, aliases, relationships, authority levels and sources live in SQLite; vectors are a derived index you can rebuild at any time.

If a question is deterministic (“what’s the battery in model X”), answer it with SQL, not with a similarity score. This single decision eliminated most hallucination complaints before they could happen: to check “this model’s battery,” the system queries SQL exactly — it never guesses through vectors.

The content model comes first: four tables (products, aliases, relations, documents/chunks). Ten documents were cut into 60 chunks, each tagged with model_code (which model it belongs to), content_type (parameter / FAQ / compare / review), authority (3 / 2 / 1) and source.

How Does Retrieval Work Without a Vector DB?

Four recall paths, filtered before fusion, merged with Reciprocal Rank Fusion (RRF). Single-path retrieval always misses; combining paths fixes most of it.

  1. Exact path (SQL) — locks the model, guaranteeing every chunk of that model becomes a candidate.
  2. Contrast path — for comparison questions (“what’s the difference between A and B”), it fetches only content_type='compare' chunks.
  3. Dense path — bge-small-zh-v1.5 embeddings (512-d) for semantic similarity.
  4. BM25 path — keyword exact match, which is what makes model names and parameter values work.

RRF merges the four by rank only, not score — the path scores live on incompatible scales (dense 0–1, BM25 0–30), so direct weighting is impossible; rank-only fusion sidesteps normalization entirely.

Filter before you fuse. Decide which data is allowed to compete (per-model isolation, authority floors) before merging paths. If you filter after fusion, dead candidates occupy your top-5 slots and good chunks get squeezed out.

Two details that are easy to skip and expensive to miss:

  • Filter-first ordering — a small design choice with an outsized effect on answer quality.
  • Model isolation — single-model questions keep only the “most specific” match. It looks trivial; it caused the biggest bug (see lesson 1).

Why Should You Evaluate Before You Tune?

Because every change moves quality in both directions, and “it seems better” is a coin flip. Chunking, recall-path count and prompts all have two-sided effects on quality; without a quantifiable measure, you cannot tell a win from a regression.

The eval was therefore the first deliverable, built before any tuning: 12 questions covering six shapes — factual parameters, model comparison, capability judgment, cross-model contamination traps, honest refusal, and stock/availability — each passing six checks:

  1. Normalization — did it correctly resolve the model (alias mapping)?
  2. Retrieval — did the expected material appear in top-5?
  3. Model isolation — did another model’s numbers leak into the answer? (most critical)
  4. Coverage — are all required points present?
  5. Post-check — any speculative wording or unsourced numbers?
  6. Refusal — did it refuse when it should?

The trajectory: 94.4% → 98.6% → 100%. Every point of improvement was forced by a specific failing case — which is exactly why the score is credible as a regression harness, and exactly why it should not be read as a benchmark.

Which Six Debugging Lessons Cost the Most Time?

The quality problems were almost never about the model — they were about data modeling, ordering bias and vocabulary gaps. These six are the gold in this report.

#LessonThe bugThe fix
1Alias normalization ≠ substring logick90ultra and K90 have no shared substring, but their model codes share a prefix; string-contains logic picks the wrong “most specific” matchUse model-code prefixes, not alias strings, to keep only the most specific match
2SQL ORDER BY = insertion-time biasThe exact path returned chunks in DB order, so later docs (UGC reviews) systematically lost RRF fusion — that is recency of insertion, not relevanceGive every exact-match chunk the same rank (1); introduce no ordering at all
3Sorting exact-path by dense score kills vector-blind spots“Photography” (user words) never matched the doc’s “imaging specs” — the chunk was #None in both dense and BM25, then dense-sorting pushed it out of top-5Uniform rank again — any ordering carries a bias
4Table content is dense-blindA multi-column spec-comparison table embeds terribly, yet it is exactly what comparison questions needThe contrast path repeats each compare-chunk 3× in RRF ≈ weight amplification
5Query expansion > tweaking the embedderUsers say “photography,” docs say “imaging specs” — a vocabulary gap the embedder cannot seeExpand “photography” → imaging / camera / rendering, retrieve each variant, keep per-chunk MAX similarity (never SUM, so one variant cannot farm the score)
6Post-check can misfireDuring an API timeout, the error string’s port number 443 was flagged as a fabricated numberVerify only against numbers that are supposed to be in the materials; never treat error output as an answer

One environmental bonus: API timeouts were infrastructure, not logic — retries, backoff, and lowering the timeout from 180s to 60s killed most of the flake.

How Much of the Method Transfers to a New Domain?

The engine ports; the thresholds do not. The exact same engine was replicated on a second, unrelated topic by changing only three things: the data, the normalization rules, and the prompt. The new domain’s independent 12-question eval also reached 100% after fixes — about 600 lines total, copied as three files (geo_build / geo_query / geo_eval as thin wrappers over the original engine).

That transfer is the real deliverable: data modeling, filter-before-fuse, uniform ranks, query expansion and eval-first discipline are portable engineering. The specific numbers are not.

Why this matters for grounding LLMs: the teams that win won’t be the ones with the biggest vector database — they’ll be the ones with a measurable eval, disciplined filtering, and the humility to treat “the model is wrong” as a prompt to check their data instead.

Why Should You Read “100%” with a Grain of Salt?

Because 100% means “this self-built eval,” nothing more. The honest limitations:

  • 12 questions I wrote myself, 6 checks each, on a 60-chunk toy corpus — small, curated, not a benchmark.
  • No real users, no A/B, no out-of-domain queries — the score says nothing about traffic you do not have.
  • One model configuration (Qwen3-8B at temperature 0.1) — a bigger or different model would shift scores.
  • Honesty is a feature, not a loophole: when data is missing, the right answer is “not found in the knowledge base,” and that refusal is something you can and should test for.

Read the number as a regression harness result: it proves the pipeline did not break. It does not prove the system is right about the world.

FAQ

Do I need a vector database to build a RAG knowledge base?

No. This build uses SQLite for the truth (entities, aliases, relations, chunk metadata) and numpy for a derived vector index aligned by chunk IDs. The relational layer answers deterministic questions; vectors handle only fuzzy semantics.

What does filter-before-fuse mean in retrieval?

Restrict which data is allowed to compete — per-model isolation, authority floors — before merging retrieval paths. If you filter after fusion, dead candidates occupy top-K slots and good chunks get squeezed out.

Why did a self-built eval matter more than the model?

Every change (chunking, recall paths, prompts) moves quality in both directions, so without a quantifiable measure, “it seems better” is a coin flip. A 12-question eval with six checks each took the project from 94.4% to 100%.

Is a 100% score reliable?

No — it is 12 self-written questions with 6 checks each, on a 60-chunk toy corpus, with no real users and no out-of-domain queries. 100% means this eval, nothing more. The method transfers; the specific numbers do not.

In Short

Put the truth in the relational store, filter before you fuse, and make the eval your first deliverable — then let failing cases, not intuition, drive the tuning. That is how a 600-line SQLite + numpy RAG build went from 94.4% to passing its own eval, and how the same method moved cleanly to a second domain. The score was never the point; the measurable path to it was.
