# 从 0 搭建一个 12 题全过的 RAG 知识库：我用一套 REDMI K90 数据演示了全过程

> 说明：本文用一套**教学用演示数据**（REDMI K90 系列虚构参数与评测资料）来讲解方法，不代表任何真实产品的评测结论，请勿据此购买任何手机。

## 引子：知识库不是"塞文档 + 让 LLM 总结"

很多人做知识库，第一步是收集一堆 PDF，第二步让大模型"基于这些资料回答"。结果用起来全是幻觉、串数据、答非所问。

我花两周时间，用一套 REDMI K90 系列的演示数据，从 0 搭了一个**能用评测来证明"没答错"**的 RAG 知识库。跑完 12 道测试题，**6 项检查全部通过、总分 100%**。

这篇文章不吹嘘，不晒炫技，只讲我踩过的坑和"为什么这么设计"。它是我认为最有价值的资产——**评测驱动迭代的完整过程**。

## 一、架构：关系库是真相，向量库只是索引

核心设计决策只有一句话：

> **业务真相全部放 SQLite，向量只是一个"派生索引"。**

- SQLite（`k90.db`）：存实体、别名、关系、文档、块、元数据、权限——**真相对在这里**；
- npy 矩阵（`vectors.npy`）：只存向量，配合 `chunk_ids.json` 对齐 ID；
- 两套库靠 `embedding_id` 一一对应，构建时做一致性校验（生产必须做）。

好处：想查"这个型号的电池"，走 SQL 精确回答，绝不靠向量猜。向量只负责"模糊语义"那一部分。

**内容建模先行。** 四张表：products（型号主数据）、aliases（别名词典：至尊版→K90-ULTRA）、relations（型号关系）、documents/chunks。10 篇文档切成 60 个块，每块都有 `model_code`（属于哪台型号）、`content_type`（参数/FAQ/对比/评价）、`authority`（权威级别 3/2/1）、`source`（来源）。

## 二、检索：四路召回 + 过滤前置 + RRF 融合

单一检索必然漏。我用了四路：

1. **精确路（SQL）**：型号锁定，保证该型号全部块成为候选；
2. **对比路**：对比类问题（"A 和 B 有什么区别"）专取 `content_type='compare'` 的块；
3. **向量路**：bge-small-zh-v1.5（512 维），语义相似；
4. **BM25 路**：关键词精确匹配（型号、参数值管用）。

然后 **RRF（倒数排名融合）** 合并四路，它们分数尺度不同（向量 0~1，BM25 0~30），直接加权没法调，RRF 只看排名不看分数，绕过了归一化问题。

两个容易被忽视的点：

- **过滤前置**：先算好"允许哪些型号的数据"，每一路召回后立即过滤，再融合。如果在融合后再过滤，无效候选会占掉 top5 名额，好内容反而挤不进来。
- **型号隔离**：单型号问题只保留"最具体"的匹配。这条看起来简单，实际踩了大坑（见下）。

## 三、评测驱动：没有这把尺子，调参全是盲改

知识库的改动（改切块、改召回路数、改 prompt）对效果的影响是**双向**的，"好像变好了"的判断几乎必然出错。所以我先建评测集，再改任何东西。

12 道题，覆盖六种形态：事实参数、型号对比、能力判断、串数据陷阱、诚实拒答、货源时效。每道题跑 6 项检查：

1. **归一化**：是否正确识别出型号（别名映射）
2. **检索**：top5 是否出现期望资料
3. **型号隔离**：答案里有没有混入其他型号的数字（最关键）
4. **要点覆盖**：必须出现的要点在不在
5. **后校验**：有没有推测性表述、有没有无来源数字
6. **拒答**：该拒绝时是否拒绝

迭代轨迹：**94.4% → 98.6% → 100%**。每一分进步，都是被某个"失败用例"逼出来的。

## 四、最有价值的资产：六个坑

### 坑 1：别名归一化的"字符串包含"陷阱
"红米k90" 和 "k90ultra" 字符串没有包含关系，但 K90 / K90-ULTRA 型号代码有**前缀关系**。用别名字符串判断谁更具体？错。要用型号 code 的前缀规则剔除宽泛匹配。一版答错，改这个就对了。

### 坑 2：精确路按 SQL 顺序 = 按入库时间排
后写入的文档（比如新增的用户评价）在精确路里永远排后面，RRF 融合后系统性垫底——**这不是相关性，这是入库时间偏见**。修法：精确路所有块给相同排名（rank=1），不引入任何顺序。

### 坑 3：精确路按向量排序 = 向量盲区的内容垫底
改成按向量分数排序后，新问题出现：某型号的影像参数块在向量路和 BM25 路**都是 #None**——用户说"拍照"，文档写"影像/主摄参数"，向量和 BM25 都找不到。按向量排之后它在精确路也垫底，掉出 top5。**任何排序都有偏见**，全 rank=1 是最公平的。

### 坑 4：同义词查询扩展，别指望调 embedding
"拍照"（口语）和"影像"（文档书面词）的词表鸿沟才是根因。修法：把"拍照"扩展成"拍照/影像/相机/成像"分别检索，逐块取**最大相似度**（用 MAX 不用 SUM，防某个块刷分）。950 这个关键参数立刻被召回。

### 坑 5：表格是向量盲区，对比内容要给它"专属权重"
"关键参数对比表"这种多列数字，向量嵌入质量天然差，但语义上恰恰是对比类问题最核心的材料。修法：对比路在 RRF 里重复 3 次 ≈ 权重放大，专职对比文档在对比问题里获得应有地位。

### 坑 6：后校验也会误报
评测时 API 超时，错误文本里的端口号 `443` 被后校验当成"编造数字"。后校验只适合核对"资料里的数字"，要注意别把错误信息当答案。

（还有一个观察：API 网络超时是环境问题，重试 + 退避 + 把超时从 180s 降到 60s 能大幅减少偶发失败。）

## 五、这套流程能迁移到什么程度？

我把同一套引擎几乎原样复制到另一个主题（"GEO 优化"），只改了数据、归一化、prompt 三处，新库 **12 题同样全过**。这验证了：**方法可迁移，参数要重测，评测驱动是让"换"不出错的尺子。**

## 六、回到原点："准确"到底靠什么？

一圈做下来，我的结论是：

> 知识库的核心不在 embedding，而在**数据建模 + 过滤纪律 + 可量化的评测**。

- 数据建模决定"能不能答对"（关系表管死真相）；
- 过滤纪律决定"会不会答串"（型号隔离、权威分级、诚实拒答）；
- 评测驱动决定"改对了没有"（12 题 × 6 检查，整轮复审）。

如果你的知识库项目还在为"为什么 AI 乱说"头疼，先问自己三句话：真相关进关系库了吗？过滤在融合之前吗？有没有一把能量化"变好/变坏"的尺子？
